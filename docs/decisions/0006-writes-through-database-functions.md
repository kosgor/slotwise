# 0006. Бронирование — только через функции базы, доступ — двумя слоями

Дата: 2026-10-19 · Статус: принято

## Коротко

Браузер разговаривает с Supabase напрямую: любой пользователь может открыть консоль и отправить
любой запрос к API. Поэтому «бронь создаётся кнопкой на сайте» — не защита. Бронь создаётся только
функцией в базе `book_slot()`: она сама берёт цену, сама проверяет расписание, и пересечения
физически невозможны из-за ограничения в таблице. Прямо записать строку в `bookings` нельзя никому,
кроме сервера.

## Контекст

На этапе 2 появились данные, которые пользователи меняют: профили, услуги, расписание, брони.
Типичные дыры в приложениях на Supabase, собранных с помощью AI: таблица без RLS, политика `using (true)`,
цена и статус, которые приходят из браузера, проверка «свободно ли» перед вставкой (гонка).

## Решение

**Два слоя доступа на каждой таблице:**

1. `GRANT` — какие таблицы и колонки роль вообще может трогать. Проект создан с выключенным
   «Automatically expose new tables», поэтому без явного `GRANT` таблица недоступна.
   Для правок — права на **колонки**: владелец может менять `display_name`, но не `status`, `slug`, `user_id`;
   клиент может менять своё имя в `profiles`, но не `role`.
2. RLS — какие строки. Одна политика на роль и действие (рекомендация линтера Supabase).

**Брони и критичные действия — функции `SECURITY DEFINER`:**

| Функция                            | Что гарантирует                                                                                                                                                       |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `book_slot(service_id, starts_at)` | цена и длительность из базы; время внутри расписания и на сетке 30 минут; не в выходной; ≥ 1 часа и ≤ 60 дней вперёд; нельзя записаться к себе; снимок данных в брони |
| `cancel_booking(id)`               | клиент — не позже чем за 24 часа; специалист и админ — в любое время до начала; чужая бронь — «не найдено» (не раскрываем, что она есть)                              |
| `apply_as_provider(…)`             | профиль создаётся со статусом `pending`, роль меняется на `provider` — пользователь не может сам выдать себе статус или роль                                          |
| `provider_busy_intervals(…)`       | занятые интервалы для расчёта слотов — без имён и почт клиентов                                                                                                       |
| `replace_availability_rules(…)`    | `SECURITY INVOKER` (права вызывающего, RLS действует): замена недели расписания одной транзакцией                                                                     |

**Пересечения — ограничение `bookings_no_overlap` (EXCLUDE USING gist)**, а не проверка в коде. Два
одновременных запроса не могут оба пройти: второй получает `exclusion_violation`, функция переводит его в
`slot_taken`. Проверено интеграционным тестом с двумя параллельными запросами к настоящему Supabase.

**Правила в двух местах — и тест, что они совпадают.** Расчёт слотов для интерфейса — TypeScript
(`lib/booking/slots.ts`), окончательная проверка — SQL в `book_slot()`. RLS-тест прогоняет каждый слот,
который показал бы интерфейс, через настоящую функцию в PGlite: все должны быть приняты.

## Компромиссы

- Линтер Supabase предупреждает «SECURITY DEFINER-функцию может вызвать authenticated/anon». Это и есть
  задуманный интерфейс; каждая функция сама проверяет `auth.uid()` и права. Предупреждения оставлены
  осознанно.
- Бизнес-правила (24 часа, 60 минут, сетка 30 минут) записаны и в SQL, и в TypeScript. Расхождение
  ловит тест согласованности, но менять их нужно в двух местах.
- `SECURITY DEFINER` обходит RLS внутри функции — значит, ошибка в функции опаснее ошибки в политике.
  Поэтому у каждой функции `set search_path = ''` и отдельные тесты.

## Пересмотреть, когда

Появится оплата (этап 3): `book_slot()` станет создавать бронь `pending_payment`, подтверждать её будет
вебхук Stripe — тоже только на сервере.
