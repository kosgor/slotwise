# 0003. Каталог на локальных seed-данных до подключения Supabase

Дата: 2026-10-16 · Статус: принято (временно)

## Контекст

План этапа 1: «данные каталога — из Supabase». Но аккаунты и деплой отложены, работаем только
локально. Локальный Supabase требует Docker, которого на машине нет.

## Решение

- Данные живут в `lib/catalog/seed-data.ts` — одном источнике правды для приложения, тестов и `supabase/seed.sql`.
- Доступ к данным разделён на три слоя:
  - `lib/catalog/source.ts` — **откуда** данные (сейчас seed, потом Supabase);
  - `lib/catalog/repository.ts` — **кэширование** (`"use cache"`, `cacheTag("catalog")`);
  - страницы — знают только `repository.ts`.
- Схема уже написана как настоящая миграция (`supabase/migrations/…_catalog.sql`) с RLS-политиками
  и представлением `catalog_providers`. `seed.sql` генерируется скриптом `npm run db:seed`.
- Миграция, seed и политики проверяются в **PGlite** (Postgres в WebAssembly) прямо в Vitest:
  `tests/rls/catalog.rls.test.ts`.

## Почему

- Страницы, кэширование и тесты не изменятся при переходе на Supabase — меняется один файл `source.ts`.
- SQL не «написан вслепую»: он реально выполняется, а тесты падают, если открыть политику или убрать
  `security_invoker` у представления (проверено поломкой).
- CI проверяет, что `seed.sql` не разошёлся с `seed-data.ts`.

## Компромиссы

- Фильтрация сейчас в памяти (`lib/catalog/query.ts`). Для 24 специалистов это мгновенно; с Supabase
  фильтры переедут в SQL-запрос к `catalog_providers`, а чистые функции останутся для тестов и проверки.
- PGlite — не Supabase: роли `anon`/`authenticated`, схема `auth` и права по умолчанию в тесте сымитированы.
  Финальная проверка политик — на настоящем Supabase-проекте (этап 2).

## Пересмотреть, когда

Появится Supabase-проект: реализовать `source.ts` через `@supabase/ssr`, применить миграцию, удалить
чтение seed из приложения (seed останется для `supabase db reset`).
