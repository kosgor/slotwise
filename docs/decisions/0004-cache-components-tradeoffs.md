# 0004. Cache Components и Partial Prerendering: что получаем и чем платим

Дата: 2026-10-16 · Статус: принято

## Коротко

Next.js 16 готовит страницы заранее, как типография печатает тираж: лендинг, тарифы и все профили
лежат готовым HTML и отдаются мгновенно. Каталог так заготовить нельзя — результаты зависят от
фильтров в адресе. Поэтому его «рамка» (заголовок, серые заглушки) отдаётся сразу, а список
дописывается в тот же ответ, когда посчитан. За эту скорость мы платим одной мелочью: если у человека выключен JavaScript, в каталоге он увидит
заглушки вместо списка. Роботы список при этом видят — он есть в HTML.

Вторая проблема — несуществующий профиль отвечал «200 OK» вместо 404 — **исправлена** (см. ниже).

## Контекст

Проект создан с `cacheComponents: true` (новая модель рендеринга Next.js 16, включена по умолчанию в
`create-next-app`). В ней:

- всё, что не зависит от запроса, пререндерится в статический HTML;
- данные кэшируются явно через `"use cache"` + `cacheLife` + `cacheTag`;
- всё, что читает данные запроса (`searchParams`, `cookies`), обязано быть внутри `<Suspense>` и
  догружается потоком (Partial Prerendering, PPR).

## Решение

Используем модель как есть:

- лендинг, тарифы, `/design-system` и все 24 профиля (`generateStaticParams`) — статические (`○`);
- `/pros` — PPR (`◐`): заголовок и скелетон уходят мгновенно, результаты по фильтрам — потоком;
- `proxy.ts` до рендеринга: канонические URL каталога (308-редирект) и настоящий 404 для
  неизвестных и неопубликованных профилей.

## Компромиссы, которые мы осознанно приняли

1. **404 для несуществующих профилей — через `proxy.ts`.** Для адреса, которого не было на сборке,
   Next.js сначала мгновенно отдаёт общую оболочку страницы (`partialPrefetching`), то есть «200 OK»
   уже отправлен, когда страница вызывает `notFound()`. Без исправления это «мягкий» 404: статус 200 и
   `noindex`. Первая версия этого ADR приняла такое поведение; на ревью решили, что это неприемлемо:
   мониторинг, аналитика и SEO-аудиты считают такие страницы живыми.
   Исправление по рекомендации документации Next.js: `proxy.ts` проверяет slug **до** рендера и
   отвечает 404 (`lib/catalog/public-slugs.ts`). Список slug держится в памяти 60 секунд, чтобы с
   Supabase не ходить в базу на каждый просмотр; цена — новый или приостановленный специалист
   учитывается с задержкой до минуты. `notFound()` в странице остаётся вторым рубежом.
   Отключить `partialPrefetching` — не вариант: он отвечает за предзагрузку при навигации и станет
   обязательным в следующей мажорной версии.
2. **Без JavaScript результаты каталога визуально остаются скелетоном.** Потоковый фрагмент приходит
   в HTML скрытым и подставляется inline-скриптом. Текст при этом **есть в HTML** — краулеры
   (поисковики и AI) его читают (проверено e2e-тестом). Статические страницы полностью видны без JS.
3. **`new Date()` нельзя вызывать при пререндере.** Год в подвале — константа, `lastModified` в
   sitemap — из данных.
4. **`dynamicParams` не поддерживается** — неизвестные slug рендерятся по запросу и получают `notFound()`.

## Почему не отключить Cache Components

Это направление Next.js (в следующей мажорной версии модель станет единственной). Статическая оболочка
даёт мгновенный первый экран, а явное кэширование понятнее старых неявных правил. Компромиссы выше
касаются краевых случаев и задокументированы.

## Пересмотреть, когда

Понадобится полноценная работа каталога без JS.
