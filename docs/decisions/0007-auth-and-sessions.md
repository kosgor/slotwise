# 0007. Авторизация: Supabase Auth, сессия в cookies, роли в базе

Дата: 2026-10-19 · Статус: принято

## Коротко

Вход — Supabase Auth через `@supabase/ssr`: сессия лежит в cookies, поэтому сервер видит её при
рендеринге. `proxy.ts` обновляет сессию на каждом запросе страницы — без этого пользователей
«выкидывает» посреди действия. Роль (клиент, специалист, админ) хранится в таблице `profiles`, и
изменить её может только сервер.

## Решения

- **Клиенты Supabase по назначению:** `public.ts` (без cookies, для кэшируемого каталога), `server.ts`
  (сессия пользователя), `browser.ts` (клиентские компоненты). Ключ с обходом RLS приложение на
  этапе 2 не использует вообще — только скрипты и тесты.
- **Обновление сессии в `proxy.ts`.** Refresh-токены одноразовые: если токен обновился, новые cookies
  должны попасть и в запрос (странице), и в ответ (браузеру). Serverless-страница сама записать cookies
  не может — поэтому это делает proxy до рендера.
- **`getClaims()`, а не `getSession()`.** `getClaims()` проверяет подпись JWT; `getSession()` доверяет
  содержимому cookie, которое пользователь может подделать.
- **Роль — в `profiles`, не в JWT.** Её нельзя изменить из браузера (нет `GRANT update (role)`), она
  проверяется на сервере на каждой странице кабинета и в RLS (`private.is_admin()`).
- **Копия роли в JWT — только для маршрутизации** (добавлено 2026-10-28). Админ работает только в
  `/admin`: с любой другой страницы, включая `/`, proxy отправляет его туда до рендера, без мелькания
  чужой страницы. Документация Next.js запрещает proxy ходить в базу на каждый запрос, поэтому роль
  кладёт в токен хук Supabase `custom_access_token_hook` (миграция `20261028000000_role_claim.sql`,
  claim `user_role`; включён в `supabase/config.toml`). Это подсказка, не право: доступ по-прежнему решают `profiles`, страницы и RLS.
  Смена роли доходит до токена при следующем обновлении (≤ 1 часа); токен без claim — proxy ничего
  не делает. Отвергнуто: редирект внутри страницы (страница успевает показаться) и запрос `profiles`
  в proxy (лишний запрос к базе на каждую страницу у каждого вошедшего).
- **Защита маршрутов в два шага:** proxy без сессии редиректит `/account`, `/dashboard`, `/admin` на вход
  (быстро, по cookie); страница проверяет роль на сервере; данные защищает RLS.
- **Ссылки из писем (подтверждение, сброс пароля, Google) → `/auth/callback`**, где одноразовый код
  меняется на сессию (PKCE: код бесполезен без cookie из того же браузера).
- **`?next=` после входа — только внутренний путь** (`lib/auth/redirect.ts`), иначе ссылка «войти» могла бы
  увести на фишинговый сайт (open redirect).
- **Одинаковые ответы** на «нет такого email» и «неверный пароль», на сброс пароля для несуществующего
  адреса — не раскрываем, какие аккаунты существуют.
- **Настройки Auth — в `supabase/config.toml`** (адреса редиректа, политика паролей), применяются
  `supabase config push` после просмотра `supabase config diff`.

## Компромиссы и ограничения

- **Почта.** Встроенная почта Supabase бесплатного проекта отправляет письма только участникам команды
  проекта и с жёстким лимитом. Регистрация через форму работает для своего адреса; для настоящих
  пользователей нужен свой SMTP — Resend, этап 3. Демо-аккаунты и тестовые пользователи создаются
  через Admin API с уже подтверждённым email.
- **Google-вход** требует OAuth-клиента в Google Cloud (`docs/setup-google-auth.md`). Код готов, кнопка
  включается флагом `NEXT_PUBLIC_AUTH_GOOGLE_ENABLED`, чтобы не показывать неработающую кнопку.
- Публичные страницы стали `◐` (частичный пререндер): меню пользователя в шапке читает сессию.
  Остальная шапка и страница по-прежнему готовый HTML.
