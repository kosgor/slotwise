# 0008. Часовые пояса: расписание в местном времени, брони в UTC

Дата: 2026-10-19 · Статус: принято

## Коротко

Специалист думает «работаю по понедельникам с 9 до 13» в своём городе — так и храним расписание. Брони
храним как точный момент времени (`timestamptz`, по сути UTC). Каждый свободный слот переводится из
местного времени специалиста в UTC, а при показе — в часовой пояс посетителя.

## Решения

- `availability_rules` — `weekday` + `start_time`/`end_time` **в поясе специалиста** (`providers.timezone`).
  Так переход на летнее время не сдвигает рабочие часы: «9:00» остаётся «9:00».
- `bookings.starts_at/ends_at` — `timestamptz`. Длительность считается в реальных минутах.
- Расчёт слотов (`lib/booking/slots.ts`) идёт по календарным дням специалиста через `@date-fns/tz`:
  - время, которого не существует (весной 02:00–02:59), пропускается;
  - время, которое повторяется (осенью 02:00–02:59), даёт один слот;
  - тесты на оба перехода (Europe/Berlin).
- Посетитель выбирает день **в своём поясе**: `/api/slots` получает `tz` браузера и считает слоты в
  границах этого дня. Подпись «Times are in your time zone (Lisbon time)» и пояс специалиста, если он другой.
- Страницы кабинета рендерятся на сервере, а сервер не знает пояс посетителя: браузер один раз кладёт его
  в cookie `tz`. Нет cookie — показываем время в поясе специалиста с явной подписью.
- Календарные даты (`"2026-11-03"`) — строки, не `Date`: арифметика дней без влияния перехода времени.

## Компромиссы

- Пояс посетителя в cookie — дополнительная cookie (не для отслеживания, только для отображения).
- Список поясов берётся из Node (`Intl.supportedValuesOf`), а проверяется Postgres (`pg_timezone_names`):
  если в одном списке пояс есть, а в другом нет, сохранение вернёт понятную ошибку.
