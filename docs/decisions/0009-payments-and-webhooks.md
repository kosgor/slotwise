# 0009. Оплата: удержание слота, вебхуки Stripe, ровно один эффект

Дата: 2026-10-20 · Статус: принято

## Коротко

Бронь подтверждает **вебхук Stripe**, а не браузер. Пока клиент платит, слот удерживается
15 минут. Каждое событие Stripe обрабатывается одной функцией базы, которая в одной транзакции
записывает id события и меняет данные. Поэтому повтор события ничего не ломает, а порядок событий
не важен. Медленное (письма, возвраты) уходит в фоновые задачи Inngest.

## Контекст

Типичные ошибки в платёжном коде:

- бронь подтверждается на странице «спасибо» — клиент закрыл вкладку, и деньги списаны, а брони нет;
  или открыл `/success` руками, и бронь есть, а денег нет;
- цена приходит из браузера;
- вебхук обрабатывается дважды (Stripe повторяет доставку) — две записи о платеже, два письма;
- события приходят не по порядку (`subscription.updated` раньше `created`) — в базе старое состояние;
- проверка подписи на распарсенном JSON — подпись не сходится или проверку отключают.

## Решение

### Путь оплаты брони

1. `book_slot()` создаёт бронь `pending_payment` с `expires_at = now() + 15 мин`. Цена — из
   таблицы услуг. Бесплатная услуга подтверждается сразу.
2. Server Action создаёт Stripe Checkout (`mode: payment`) с суммой **из строки брони** и
   `booking_id` в `metadata`, сохраняет id сессии и перенаправляет на страницу Stripe.
3. Stripe присылает `checkout.session.completed` → `stripe_checkout_completed()` → `confirmed`
   и строка в `payments`.
4. Страница `/account/bookings/[id]` ничего не подтверждает. Она показывает статус из базы и
   опрашивает его раз в 2 секунды, пока не придёт вебхук.

### Удержание слота: почему 15 минут, а Checkout живёт 31

У Stripe минимальный срок жизни Checkout — 30 минут. Мы держим слот 15 минут (продлить можно до
25 минут от создания), а фоновая задача раз в 5 минут переводит просроченные брони в `expired` и
закрывает их Checkout (`sessions.expire`). Если оплата всё же успела пройти после истечения:

- слот ещё свободен → бронь восстанавливается (`expired` → `confirmed`);
- слот уже занял другой → результат `refund_needed`, деньги возвращаются автоматически и клиенту
  уходит письмо с объяснением.

Просроченное удержание не блокирует слот даже до прихода задачи: `provider_busy_intervals` его не
показывает, а `book_slot()` помечает мешающие просроченные брони сам.

### Надёжность вебхуков

| Правило                               | Как сделано                                                                                                                                                                           |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Подпись на сыром теле                 | `await request.text()` → `Stripe.webhooks.constructEvent(body, signature, secret)`. Нет подписи или она чужая → 400, база не тронута                                                  |
| Идемпотентность                       | Таблица `stripe_events` (PK = id события). Каждая функция вебхука начинает с `insert … on conflict do nothing`: если строка уже была — `duplicate`, данные не меняются                |
| Событие и эффект — в одной транзакции | Одна Postgres-функция на эффект: `stripe_checkout_completed`, `stripe_checkout_expired`, `stripe_charge_refunded`, `stripe_sync_subscription`. Ошибка → откат обоих → Stripe повторит |
| Не зависеть от порядка                | Подписки перечитываются из Stripe (`subscriptions.retrieve`) на каждом событии. Возврат хранит **итоговую** сумму (`greatest`). `expired` после оплаты игнорируется                   |
| Быстрый 200                           | В обработчике только запрос к базе. Письма и возвраты — события Inngest                                                                                                               |
| Задачи не теряются и не дублируются   | id события Inngest = id события Stripe. Повтор вебхука отправляет то же событие, Inngest его отбрасывает. Если Inngest недоступен — 500, Stripe повторит                              |
| Платёж не записан дважды              | `payments.stripe_payment_intent_id` — `unique`                                                                                                                                        |

### Возвраты

Отмена оплаченной брони: `cancel_booking()` (правило 24 часов — в базе) → сразу
`refunds.create` с ключом идемпотентности. Сумму возврата база узнаёт только из вебхука
`charge.refunded`: один источник правды. Если Stripe недоступен, фоновая задача каждые 5 минут
находит отменённые и просроченные брони с невозвращёнными деньгами и повторяет возврат.

### Подписка специалиста

- Checkout `mode: subscription`, цены находятся по `lookup_key` (`npm run stripe:setup` создаёт их).
  В `.env` нет id цен.
- `provider_subscriptions` пишет только вебхук. Pro действует, пока статус `active` или `trialing`.
  При `past_due` подписка остаётся, но действуют лимиты Free и показывается баннер.
- Лимит Free (3 активные услуги) проверяет **триггер в базе**, а не скрытая кнопка.
- Управление (карта, смена периода, отмена, счета) — Stripe Customer Portal.

### Событие — только уведомление

Из события читается только id объекта (сессии, платежа, счёта, подписки); сам объект
перечитывается через API. Это решает три задачи сразу:

- порядок событий не важен — всегда видно текущее состояние;
- версия API, в которой Stripe отрисовал событие, не важна. Аккаунт этого проекта закреплён на
  2019-02-19, и в его событиях нет полей, которые читает код; SDK читает объекты в своей версии;
- правильно подписанное, но «странное» событие (`expired` для открытой сессии) ничего не меняет.

Цена — один запрос к API на вебхук (~200 мс), Stripe отдельно рекомендует этот подход.

### Один аккаунт Stripe на все окружения (добавлено 2026-10-27)

Демо и в продакшене работает в test mode, поэтому local, staging и production делят один аккаунт
Stripe, а Stripe шлёт события аккаунта на **все** endpoint-ы. Без защиты оплата со staging приходит
на прод-вебхук, брони там нет, функция бросает `booking_not_found`, вебхук отвечает 500, и Stripe
повторяет событие до 3 дней.

Решение — метка базы в metadata (`slotwise_db` = ref проекта Supabase, `lib/stripe/db-tag.ts`) на
сессии Checkout, платеже (а значит и на charge) и подписке. Обработчик, перечитав объект, отвечает
`foreign` (200, без изменений), если метка чужая. Local и staging работают с одной dev-базой — метка у
них общая, и обрабатывать можно в любом из них: повтор отсекает `stripe_events`.

Отвергнуто: отдавать 200 на любую «ненайденную» бронь. Тогда ошибка в нашем коде (бронь не
записалась) тоже молча проглатывалась бы; чужое окружение должно определяться явно. Объекты без метки
(созданы до неё, есть только в dev) обрабатываются как раньше. Риск один: возврат по старой dev-брони
после деплоя придёт в прод и будет повторяться. Единственная старая подписка уже отменена (проверено 2026-10-27), а
старые оплаты лучше не возвращать после запуска прода.

### Одна валюта

В Checkout брони выключено Adaptive Pricing: иначе Stripe показывает и списывает цену в валюте
клиента (евро), и суммы оплаты и возвратов расходятся с ценой специалиста. Если включится снова,
обработчик сверяет исходную сумму (`currency_conversion`), а не сконвертированную.

## Последствия

- Без запущенного `stripe listen` локально брони остаются «ждут оплату» — это видно сразу.
- Секретный ключ Supabase теперь нужен приложению: только в `lib/supabase/admin.ts` (вебхуки,
  фоновые задачи, создание клиента Stripe), с `import "server-only"`.
- Stripe Connect (выплаты специалистам) не делаем: деньги приходят на счёт платформы. Это
  отдельное расширение после этапа 5.
