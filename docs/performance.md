# Замеры производительности

Lighthouse 12, мобильный профиль (симуляция слабого телефона и медленного 4G), продакшен-сборка
(`npm run build && npm run start`), локально. Медиана из 3 прогонов, если не указано иное.
Реальный LCP на этой машине < 1 с; цифры ниже — модель Lighthouse (см. ADR 0005).

## Этап 4, британский каталог (2026-10-30)

| Страница               | Performance | LCP   | TBT    | Accessibility | Best Practices | SEO  |
| ---------------------- | ----------- | ----- | ------ | ------------- | -------------- | ---- |
| `/` (медиана из 5)     | 90          | 3,6 с | 109 мс | 100           | 100            | 100  |
| `/pros`                | 94          | 3,1 с | 46 мс  | 100           | 100            | 100  |
| `/pros/anna-yoga`      | 92          | 3,3 с | 101 мс | 100           | 100            | 100  |
| `/pricing`             | 91          | 3,5 с | 60 мс  | 100           | 100            | 100  |
| `/pros/anna-yoga/book` | 93          | 3,2 с | 51 мс  | 100           | 100            | 66 * |

Lighthouse 12.8.2. CLS 0 на всех страницах, FCP 0,9 с (на странице записи 1,2 с).

**По сравнению с этапом 3:** баллы в пределах шума. TBT ниже на всех страницах. LCP на главной и
`/pricing` вырос на 0,5 с. LCP-элемент везде — заголовок `h1`, то есть текст, а не картинка. Скриптов
в HTML главной теперь около 290 КБ в gzip, на этапе 3 было около 200 КБ. Среди них — Sentry: отдельный
чанк на 14 КБ и часть основного чанка. Sentry добавлен на этапе 4 и грузится, даже когда DSN нет.
**Гипотеза не проверена:** по совету выше её нужно подтвердить сборкой без Sentry и сравнением
загруженных файлов, а не оценкой Lighthouse.

| `/pros/anna-yoga/book` | 90          | 3,4 с | 171 мс | 100           | 100            | 66 * |

\* Страница записи намеренно закрыта от индексации (`noindex`) — Lighthouse снимает за это баллы SEO.
Так и задумано: страница записи не должна попадать в поиск.

**По сравнению с этапом 1** (главная 90, каталог 95, профиль 94, тарифы 91): изменений в пределах
шума, кроме профиля (−4). JS до события `load` — около 200 КБ, как и раньше. Общий объём JS вырос
до ~300 КБ за счёт **фоновой предзагрузки** после загрузки: на каждой странице появилась ссылка
«Sign in», и Next.js заранее подтягивает код страницы входа (формы, Zod, React Hook Form).
На скорость первого показа это не влияет.

**Шум.** Первый прогон главной дал 85 (TBT 336 мс), повтор — 91, медиана из 5 — 90. Одному
прогону Lighthouse верить нельзя.

**Ошибка в анализе (для истории).** Я решил, что Zod попадает на главную через импорт `signOut` из
модуля с Server Actions, и вынес функцию в отдельный файл. Сравнение списков загруженных файлов
показало, что изменилось только имя чанка меню, а Zod и до, и после грузился фоновой предзагрузкой.
Правка откатана. Гипотеза о бандле проверяется сравнением загруженных файлов, а не оценкой
Lighthouse.

## Как повторить

```bash
npm run build && npx next start -p 3100
npx lighthouse http://localhost:3100/ --form-factor=mobile --chrome-flags="--headless=new" --view
```

Перед замером закрыть лишние программы; брать медиану минимум из 3 прогонов.
