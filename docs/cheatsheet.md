## Server Components и Client Components

В App Router **по умолчанию каждый компонент серверный**. Клиентский — с `"use client"` первой строкой файла.

|                 | Server Component                                           | Client Component                                       |
| --------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| Где выполняется | Только на сервере                                          | На сервере (SSR в HTML) **и** в браузере               |
| JS в браузере   | Нет                                                        | Да                                                     |
| Можно           | `async/await`, запросы в базу, секреты, тяжёлые библиотеки | `useState`, `useEffect`, `onClick`, `window`, анимации |
| Нельзя          | Хуки состояния, события, браузерные API                    | Секреты, прямой доступ к базе с правами сервера        |

- Серверная страница + маленькие клиентские «острова» только там, где нужен интерактив.
- `"use client"` действует на файл **и всё, что он импортирует** — ставить как можно ниже по дереву.
- Зачем: меньше JS → быстрее загрузка (Lighthouse), контент виден без JS (SEO, AI-краулеры).
- **Hydration** — когда JS клиентского компонента загрузился и «оживил» уже показанный HTML.

**Как проверить, где выполнился код** (`console.log` в dev-режиме Next.js 16):

- В консоли браузера с меткой `Server` / `Prerender` — выполнился **на сервере**, Next.js переслал лог в браузер.
- Без метки — выполнился **в браузере**.
- `Prerender` — страница статическая, рендерится заранее, а не на каждый запрос.
- В dev React рендерит дважды (Strict Mode) — повтор лога нормален.

## Переменные окружения и NEXT_PUBLIC\_

**Переменная окружения** — настройка снаружи кода (адрес базы, ключ API). Один код — разные значения для dev и prod, секреты не попадают в git.

- `.env.example` — в git, имена без значений (документация).
- `.env.local` — не в git, реальные значения. Next.js читает его **при старте** → после правки перезапусти `npm run dev`.
- На сервере: `process.env.STRIPE_SECRET_KEY`.

**`NEXT_PUBLIC_`** — значение **подставляется в JS-бандл при сборке** и видно любому посетителю в DevTools. Без префикса в браузере будет `undefined`.

| Ключ                                | Где               | Почему                                           |
| ----------------------------------- | ----------------- | ------------------------------------------------ |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | `NEXT_PUBLIC_` ✅ | Публичный по задумке, все запросы ограничены RLS |
| `SUPABASE_SERVICE_ROLE_KEY`         | только сервер ❌  | **Обходит RLS** — полный доступ ко всем данным   |
| `STRIPE_PUBLISHABLE_KEY`            | `NEXT_PUBLIC_` ✅ | Умеет только открыть форму оплаты                |
| `STRIPE_SECRET_KEY`                 | только сервер ❌  | Списания, возвраты, данные всех клиентов         |
| `OPENAI_API_KEY`                    | только сервер ❌  | Чужие запросы к модели за твой счёт              |

Правило: ключ даёт права, которых не должно быть у случайного посетителя, → без `NEXT_PUBLIC_`.

### Клиентский компонент получил `undefined` вместо секретного ключа

`undefined` — не баг, а защита. Чинить не ключ, а место выполнения кода.

**Делаешь:** переносишь код с ключом на сервер (Server Action / API route). Клиент получает только результат — например, ссылку на оплату.

```ts
"use server";
export async function startCheckout(bookingId: string) {
  const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);
  const booking = await getBookingFromDb(bookingId); // цена из базы, не из браузера
  const session = await stripe.checkout.sessions.create({/* ... */});
  return session.url; // клиенту — только ссылка
}
```

**Не делаешь:**

- ❌ Не переименовываешь в `NEXT_PUBLIC_STRIPE_SECRET_KEY` — ошибка уйдёт, ключ окажется у всех.
- ❌ Не передаёшь ключ пропом из серверного компонента в клиентский — пропсы сериализуются в HTML.
- ❌ Не хардкодишь в коде — уйдёт в git.

Если `undefined` **на сервере** — другая проблема: нет в `.env.local`, опечатка в имени, не перезапущен dev-сервер.

## Server Action и API route

Оба выполняют код на сервере. Выбор — по вопросу **«кто вызывает?»**.

**Server Action** — функция с `"use server"`, из своего UI вызывается как обычная функция (Next.js сам делает POST).

```ts
"use server";
export async function cancelBooking(bookingId: string) {
  const user = await getUser(); // проверка прав на сервере
  // ...
}
```

**API route** — файл `app/api/.../route.ts` с `GET`/`POST`, настоящий HTTP-эндпоинт с URL.

```ts
// app/api/webhooks/stripe/route.ts → POST /api/webhooks/stripe
export async function POST(req: Request) {
  const body = await req.text(); // сырое тело для проверки подписи
  return new Response("ok");
}
```

|              | Server Action                                | API route                                                |
| ------------ | -------------------------------------------- | -------------------------------------------------------- |
| Кто вызывает | Твой интерфейс                               | Кто угодно по URL: Stripe, Inngest, мобильное приложение |
| Как          | Как функцию                                  | HTTP / `fetch`                                           |
| В Slotwise   | Бронь, отмена, профиль, услуги, старт оплаты | Вебхуки Stripe, стриминг AI-чата, Inngest                |

- **Чтение данных для страницы** — обычно ни то ни другое: Server Component читает из базы напрямую.
- **Server Action — тоже публичный эндпоинт**, его можно вызвать в обход кнопки с любыми аргументами → внутри всегда проверка прав и Zod.

## RLS (Row Level Security)

Функция Postgres: правила доступа **на уровне строк**. База сама решает, какие строки показать текущему пользователю.

Почему критично в Supabase: браузер ходит в базу **напрямую** с anon key. Без RLS запрос из консоли

```js
supabase.from("bookings").select("*");
```

вернёт брони **всех** клиентов. С политикой:

```sql
alter table bookings enable row level security;

create policy "client sees own bookings" on bookings
  for select using (client_id = auth.uid()); -- auth.uid() — id пользователя из токена
```

тот же запрос вернёт только его брони. Обойти из браузера нельзя.

- **RLS не настраивается сам.** Таблицы из SQL-миграций создаются **без** RLS — включать и писать политики нужно самому.
- RLS включён, политик нет → доступ закрыт всем (безопасно, но приложение ничего не видит).
- Правило проекта: каждая новая таблица — `enable row level security` + политики **в той же миграции**.
- RLS vs проверка в коде: проверку можно забыть в одном из 30 мест, RLS действует на любой запрос к таблице.
- `service_role` обходит RLS → только на сервере, только в вебхуках и фоновых задачах.

## npm run dev и npm run start

|             | `npm run dev`                        | `npm run start`                          |
| ----------- | ------------------------------------ | ---------------------------------------- |
| Что это     | Сервер разработки                    | Запуск готовой сборки                    |
| Перед этим  | Ничего                               | `npm run build`                          |
| Компиляция  | По требованию, при открытии страницы | Заранее, при `build`                     |
| Правки кода | Видны сразу (hot reload)             | Не видны без нового `build`              |
| Код         | Не минифицирован, доп. проверки      | Минифицирован, оптимизирован             |
| Скорость    | Медленно                             | Как на проде                             |
| Для чего    | Писать код                           | Проверить реальное поведение, Lighthouse |

Эксперимент: в статической странице `console.log` при `build && start` срабатывает **один раз во время сборки** — страница отрендерена заранее. В `dev` — на каждый запрос.

Ошибки вида «prerender failed» видны только при `npm run build`.

## Превью-деплои

Каждая ветка или PR автоматически собирается на **отдельный URL**, прод (`main`) не затрагивается.

- Зачем: проверить изменение в реальном окружении до слияния, отправить ссылку клиенту или ревьюеру, гонять e2e-тесты на настоящей сборке.
- **Не только Vercel**: Netlify (Deploy Previews), Cloudflare Pages, Render, Railway, самописные на GitHub Actions / Bitbucket Pipelines. Общее название — preview / ephemeral environments.
- У переменных окружения три области: Development, Preview, Production. Превью смотрят в **тестовую** базу и test-ключи Stripe.
- Локальный аналог: `npm run build && npm run start`.

В Slotwise деплой отложен — пока работаем только локально.

## shadcn/ui

**Не библиотека в `node_modules`, а генератор кода**: команда копирует исходник компонента в проект, дальше он твой.

```bash
npx shadcn@latest add dialog            # один компонент → components/ui/dialog.tsx
npx shadcn@latest add select tabs sheet # несколько сразу
npx shadcn@latest add                   # интерактивный список всех компонентов
```

```tsx
import { Button } from "@/components/ui/button";

<Button>Записаться</Button>
<Button variant="outline" size="lg">Подробнее</Button>
<Button asChild><Link href="/pricing">Тарифы</Link></Button>
```

- Цвета — CSS-переменные в `app/globals.css` (`--primary`, `--muted-foreground`…). Меняешь токен — перекрашиваются все компоненты.
- Настройки CLI — `components.json`.
- **Два слоя компонента**: примитив (поведение: клавиатура, фокус, `aria`, Esc) из headless-библиотеки + стиль (Tailwind).
- Стиль называется `<библиотека>-<пресет>`: `radix-nova` = Radix + пресет Nova, `base-nova` = Base UI + тот же пресет. Выглядят одинаково, разное «под капотом». У нас `radix-nova` — см. [ADR 0002](decisions/0002-shadcn-on-radix.md).

## cn, cva, Slot

**`cn`** = `clsx` + `tailwind-merge`.

- **Конфликты у Tailwind-классов есть**: в `class="px-2.5 px-6"` побеждает не тот, что правее, а тот, что ниже в сгенерированном CSS — порядок решает Tailwind, не ты.
- `tailwind-merge` понимает, что `px-2.5` и `px-6` — одно свойство, и выкидывает первый → твой `className` гарантированно перебивает базовые стили.
- `clsx` — условные классы: `cn("p-4", isActive && "bg-primary", { "opacity-50": disabled })`.

**`cva`** (class-variance-authority) — варианты компонента таблицей вместо `if`:

```ts
const buttonVariants = cva("базовые классы", {
  variants: { variant: { default: "...", outline: "..." }, size: { sm: "...", lg: "..." } },
  defaultVariants: { variant: "default", size: "default" },
});
```

`VariantProps<typeof buttonVariants>` выводит типы пропсов автоматически — TypeScript подсказывает допустимые `variant` и `size`.

**`Slot`** (Radix) — для `asChild`: компонент не рендерит свой тег, а «надевает» стили и пропсы на дочерний элемент.
`<Button asChild><Link/></Button>` → один `<a>` со стилями кнопки вместо невалидного `<button><a>`.

| Категория          | Что меряет                                                                              |

## Доступность (WCAG)

Цель проекта — **WCAG 2.2 уровня AA**. Пункты по этапам — в [PLAN.md](PLAN.md).

- Семантика: `<main>`, `<nav>`, один `<h1>`, действия — `<button>`, переходы — `<a>`.
- Всё работает с клавиатуры, фокус виден, Esc закрывает модалки, фокус возвращается.
- Контраст: текст ≥ 4.5:1, крупный текст и границы полей ≥ 3:1.
- Информация не только цветом; `alt` у картинок; `aria-label` у кнопок-иконок.
- Динамические изменения (результаты фильтра, статус оплаты, ответ AI) объявляются через `aria-live`.
- Формы: `<label>`, ошибки через `aria-describedby` + `aria-invalid`, правильный `autocomplete`.
- `prefers-reduced-motion` отключает анимации.
- Автопроверки (axe, Lighthouse) ловят лишь ~30–40% проблем → обязательна ручная проверка клавиатурой и скринридером (NVDA, VoiceOver).
- Radix даёт правильное поведение примитивов (фокус, `aria`) — это одна из причин его выбора.

## ADR (docs/decisions)

**Architecture Decision Record** — запись об одном архитектурном решении: контекст, решение, почему, компромиссы, когда пересмотреть. Пишется в момент решения; если решение меняется — новая запись.

Зачем:

- Через полгода ответ на «почему тут нет Prisma?» лежит в файле, а не в голове.
- Для портфолио — доказательство, что ты **принимаешь решения** и понимаешь их цену (уровень senior / takeover).
- На созвоне: «расскажите о техническом решении» → открываешь запись.

Как показывать: раздел «Ключевые решения» в README со ссылками на 3–4 ADR; в отклике — ссылка на ADR, подходящий к вакансии. Одна страница на запись, только реальные развилки.

Шаблон — [decisions/README.md](decisions/README.md).

## Cache Components и `"use cache"`

В проекте включено `cacheComponents: true` — новая модель Next.js 16.

- **Статика по умолчанию.** Всё, что не зависит от запроса, рендерится заранее (`○` в выводе `next build`).
- **`"use cache"`** в начале функции или компонента кэширует результат. Аргументы становятся ключом кэша.
  - `cacheLife("hours")` — сколько живёт запись.
  - `cacheTag("catalog")` — метка, чтобы потом сбросить кэш: `revalidateTag("catalog")` (этап 2, когда специалист меняет профиль).
- **Данные запроса** (`searchParams`, `cookies`, `headers`) известны только при запросе → компонент, который их читает, должен быть внутри `<Suspense>`.
- **Partial Prerendering (PPR, `◐`)** — статическая оболочка уходит мгновенно, динамическая часть догружается потоком.
- `new Date()`, `Math.random()` при пререндере запрещены — результат был бы «заморожен» в HTML.

Чем платим (ADR 0004):

- **«Мягкий» 404 — ловушка:** при стриминге статус 200 уже отправлен до `notFound()`. Next.js ставит `noindex`, но мониторинг и SEO-аудиты считают страницу живой. Исправление — проверка в `proxy.ts` до рендера, она отдаёт настоящий 404.
- **Без JS** потоковая часть остаётся за скелетоном (её подставляет inline-скрипт), хотя текст есть в HTML и краулеры его видят.

## Фильтры в URL

- **URL — источник правды.** Фильтры можно отправить ссылкой, добавить в закладки, поисковик видит каждую комбинацию.
- **Обычная GET-форма** (`next/form`): без JS работает как HTML-форма, с JS — клиентская навигация без перезагрузки.
- **Нативный `<select>`** вместо Radix Select в фильтрах: работает без JS, на телефоне открывает системный выбор, доступен без ARIA.
- **Атрибут `form="id"`** привязывает поле вне `<form>` к форме — так селект сортировки сохраняет фильтры.
- **Чистые URL:** GET-форма отправляет и пустые поля (`?q=&city=`). `CleanGetForm` отключает пустые поля на момент отправки; без JS `proxy.ts` делает 308 на каноническую версию и сохраняет `utm_*`.
- **Zod с `.catch()`** — неверный параметр в URL превращается в «не задан», страница никогда не падает от ручной правки URL.

### `proxy.ts` (бывший middleware)

Код до рендеринга страницы: редиректы, заголовки, быстрые проверки. **Не для медленных запросов к данным.** На этапе 2 сюда добавится обновление сессии Supabase.

## SEO и AEO

| Что                            | Где                          | Зачем                                                                     |
| ------------------------------ | ---------------------------- | ------------------------------------------------------------------------- |
| `metadata`, `generateMetadata` | `layout.tsx`, страницы       | `<title>`, description, canonical, Open Graph                             |
| `opengraph-image.tsx`          | `app/`                       | Картинка-превью для ссылок в Slack, LinkedIn, Upwork                      |
| `sitemap.ts`                   | `app/`                       | Список всех URL для поисковиков                                           |
| `robots.ts`                    | `app/`                       | Что можно индексировать; AI-краулеры разрешены явно                       |
| JSON-LD                        | `components/seo/json-ld.tsx` | Структурированные данные: Organization, WebSite, Person, Service, FAQPage |
| `llms.txt`                     | `app/llms.txt/route.ts`      | Карта сайта в Markdown для языковых моделей                               |

- **AEO** (Answer Engine Optimization) — оптимизация под ответы AI-ассистентов: контент в HTML, разрешённые AI-краулеры, структурированные данные, `llms.txt`.
- **JSON-LD и XSS:** `JSON.stringify` не экранирует `</script>`. Если в био специалиста окажется `</script><script>…`, тег закроется и выполнится чужой код. Поэтому `serializeJsonLd` заменяет `<` на `\u003c` (есть тест).
- FAQ на нативных `<details>`: ответы есть в HTML, в отличие от JS-аккордеона, который удаляет закрытые панели.

### AEO подробно: три пункта плана

Пункт плана: «AEO: `llms.txt`, контент виден без JS, AI-краулеры не заблокированы».

**Зачем вообще.** Люди всё чаще ищут не в Google, а спрашивают ChatGPT, Claude или Perplexity:
«найди преподавателя йоги онлайн до $40». Ассистент отвечает по тому, что его робот (краулер)
прочитал на сайтах. Если робот сайт не прочитал или не понял — в ответе сайта не будет.
AEO (Answer Engine Optimization) — набор мер, чтобы робот прочитал и понял.

**1. AI-краулеры не заблокированы.**
У каждой AI-компании свой робот: `GPTBot` и `OAI-SearchBot` (OpenAI), `ClaudeBot` (Anthropic),
`PerplexityBot`, `Google-Extended` (Gemini). Сайт может запретить их в `robots.txt` — многие так
делают, чтобы контент не брали для обучения. Для каталога услуг нам выгодно обратное: чем чаще
ассистенты цитируют Slotwise, тем больше клиентов. Поэтому в `app/robots.ts` они перечислены
явно и разрешены (кроме личных разделов). Проверить: открыть `/robots.txt`.

**2. `llms.txt`.**
Обычная страница — это HTML с меню, кнопками и скриптами; модели приходится выковыривать из неё
смысл. `llms.txt` — предложенный стандарт (llmstxt.org): короткий текстовый файл в Markdown в корне
сайта «для моделей» — что это за сайт, главные страницы, список специалистов с ценами, FAQ.
Аналог `sitemap.xml`, только для языковых моделей и с содержанием. Генерируется из тех же данных,
что и страницы (`app/llms.txt/route.ts`), поэтому не устаревает. Проверить: открыть `/llms.txt`.

**3. Контент виден без JS.**
Браузер получает HTML, а потом выполняет JavaScript. Многие AI-краулеры JavaScript **не выполняют**:
они читают только тот HTML, что пришёл с сервера. Если сайт рисует контент в браузере
(классическое SPA на React: сервер присылает пустой `<div id="root">`), робот увидит пустую страницу.
У нас страницы рендерятся на сервере (Server Components), и текст есть в HTML сразу.
Проверить: `curl http://localhost:3000/pros/anna-yoga` — в ответе видно имя, услуги и цены.

**Оговорка про каталог: «результаты есть в HTML, но визуально за скелетоном».**
Страница `/pros` отдаётся в два приёма (Partial Prerendering):

1. Сразу уходит готовый каркас: заголовок и **скелетон** — серые прямоугольники на месте карточек.
   Поэтому страница появляется мгновенно.
2. Следом в том же ответе приходит настоящий список специалистов — но в **скрытом** блоке
   (`<div hidden>`). Крошечный встроенный скрипт переставляет его на место скелетона.

Что из этого следует:

| Кто читает               | Что видит           | Почему                                                      |
| ------------------------ | ------------------- | ----------------------------------------------------------- |
| Обычный браузер          | Список специалистов | Скрипт сработал за миллисекунды                             |
| AI-краулер, поисковик    | Список специалистов | Читает HTML как текст; скрытый блок для него такой же текст |
| Человек с выключенным JS | Скелетон            | Скрипт, который переставляет блок, не выполнился            |

Для AEO и SEO пункт выполнен (проверено e2e-тестом «catalog results are in the HTML for crawlers»).
Людей с выключенным JavaScript — доли процента; это осознанный компромисс (ADR 0004).
Лендинг, профили и тарифы готовы целиком заранее и видны без JS полностью.

**Как ответить на собеседовании.**

- _«Как сделать, чтобы сайт попадал в ответы ChatGPT/Perplexity?»_ —
  «Три вещи: не блокировать их краулеры в robots.txt, отдавать контент в серверном HTML, потому что
  многие AI-краулеры не выполняют JavaScript, и давать структуру — JSON-LD по schema.org и
  llms.txt с кратким описанием сайта. В Slotwise всё это есть и проверяется тестами».
- _«Чем SPA плохо для SEO?»_ —
  «Сервер присылает пустую страницу, контент появляется только после выполнения JS. Google JS
  выполняет, но с задержкой; большинство AI-краулеров — нет. Решение — серверный рендеринг или
  пререндер, как Server Components в Next.js».
- _«У вас стриминг — краулер увидит контент?»_ —
  «Да: потоковая часть приходит в том же HTML-ответе, просто в скрытом блоке. Робот читает её как
  текст — мы проверяем это тестом, который запрашивает страницу без JS и ищет имена специалистов.
  Визуально без JS остаётся скелетон, это задокументированный компромисс».

## RLS на практике

```sql
alter table public.providers enable row level security;

create policy "Approved providers are public"
  on public.providers for select to anon, authenticated
  using (status = 'approved');
```

- **Нет политики на запись → писать может только service role.** INSERT от `anon` падает, UPDATE/DELETE молча меняют 0 строк.
- **Представления обходят RLS**, если не указать `with (security_invoker = true)`: по умолчанию представление выполняется с правами владельца.
- **Два слоя защиты.** `GRANT` решает, к каким таблицам роль вообще имеет доступ и какие операции ей разрешены; RLS — какие строки внутри. Исторически Supabase выдавал `anon` права на все новые таблицы, и вся защита держалась на RLS. Наш проект создаётся с выключенным «Automatically expose new tables»: права выдаются только явными `GRANT` в миграциях (`…_explicit_grants.sql`). Забыли `GRANT` — таблица недоступна (ошибка видна сразу), а не открыта всем.
- **Enable automatic RLS** — триггер Supabase включает RLS на каждой новой таблице, даже если миграция забыла. Мы всё равно включаем явно.
- **PGlite** — настоящий Postgres в WebAssembly. Миграция и политики проверяются в обычном `npm test`, без Docker.

## Производительность: что узнали замерами

- **Lighthouse по умолчанию моделирует** слабый телефон (`throttling: simulate`). Реальный LCP у нас 0,8 с, смоделированный — около 3 с. Модель считает, что отрисовка ждёт весь JS, загруженный до неё → главный рычаг — меньше JS на старте.
- **Серверный код может утечь в бандл.** Клиентский компонент импортировал константу из файла, который импортирует Zod → +31 КБ в браузере. Лечение: константы — в отдельный файл без зависимостей.
- **«Оптимизация» может ухудшить.** Асинхронный `LazyMotion` поднял TBT со 186 до 300+ мс. Без замера мы бы его оставили (ADR 0005).
- **Ленивая загрузка по намерению:** мобильное меню (Radix Dialog) грузится при наведении, фокусе или касании кнопки, а не на каждой странице.
- **CSS вместо JS** для декоративного: появление при прокрутке через `animation-timeline: view()` — 0 КБ JS.
- **Шум измерений:** один прогон Lighthouse ничего не доказывает — берём медиану из 3+ прогонов.

## Вопросы после этапа 1

### Как собрать систему компонентов, а не верстать страницы по одной

1. **Токены.** Выписать из макета все цвета, размеры шрифтов, отступы, радиусы и дать им имена (`primary`, `muted-foreground`, `radius`). Если в макете 7 почти одинаковых серых — договориться о 2–3.
2. **Инвентаризация.** Пройти по всем экранам и найти повторы: кнопки, поля, карточки, бейджи. Каждый повтор — кандидат в компонент.
3. **Варианты, а не копии.** Кнопка одна, у неё варианты (`default`, `outline`, `ghost`) и размеры (`sm`, `lg`) — это `cva` в `components/ui/button.tsx`. Не «синяя кнопка в шапке» и «синяя кнопка в карточке».
4. **Состояния.** Для каждого компонента: hover, focus, disabled, loading, error, empty.
5. **Слои.** `components/ui/` — базовые кирпичи без бизнес-смысла. `components/features/` — кирпичи предметной области (`ProviderCard` = Avatar + Badge + Rating). Страницы только собирают их.
6. **Витрина** (`/design-system` или Storybook) — видно, что уже есть, и не появляется вторая такая же кнопка.

Признак, что система работает: новая страница собирается из готовых компонентов почти без нового CSS.

### Почему токены в `app/globals.css`, а не в `tailwind.config`

В Tailwind v4 конфигурация переехала в CSS: директива `@theme` в `globals.css` заменяет `tailwind.config.js` (это формат v3, план написан по старой привычке). `@theme inline { --color-primary: var(--primary); }` создаёт классы `bg-primary`, `text-primary`, а сами значения лежат в CSS-переменных `:root` и `.dark`. Плюс: тема переключается сменой переменных, без пересборки.

### Откуда текущий дизайн

Дизайнера и макетов нет. Основа — стиль `radix-nova` из shadcn (размеры, радиусы, вид компонентов). Палитру (бирюзовый основной, тёплый нейтральный фон) выбрал AI и проверил контраст тестом. Раскладка страниц — типовые паттерны SaaS-лендингов. Для портфолио «Figma → код» это не замена работе с настоящим макетом.

### `/design-system` и Storybook

- **`/design-system`** — страница в самом приложении. Пункт плана (экспонат для портфолио). Живой стайлгайд — известная практика (GOV.UK, Shopify Polaris), но в продуктовых командах обычно используют Storybook.
- **Storybook** — отдельный инструмент: каждый компонент разрабатывается изолированно, на каждое состояние пишется «история», есть автодокументация, a11y-аддон, интерактивные тесты, визуальные регрессионные тесты (Chromatic). Запускается отдельно от приложения.
- **Почему пока не Storybook:** для одного разработчика и 16 компонентов это лишняя инфраструктура, а `/design-system` видна прямо в демо. Storybook часто встречается в вакансиях — его можно добавить отдельной задачей.

### `next/font`

- При запуске `next dev` или `next build` Next.js скачивает файлы шрифта (у нас Geist с Google Fonts) и кладёт в `.next/static/media`. Поэтому шрифт правильный и при разработке: первый запуск нужен с интернетом, дальше работает из кэша.
- Генерирует `@font-face` с уникальным именем, вставляет `<link rel="preload">` и подбирает резервный системный шрифт с поправкой размеров (`size-adjust`), чтобы текст не прыгал при подмене шрифта.
- В браузер шрифт приходит с твоего домена, без запроса к Google — быстрее и без передачи IP посетителя третьей стороне.

### `next/image`

`<Image src="/images/providers/anna-yoga.jpg" width={80} height={80}>` превращается в `<img srcset="/_next/image?url=…&w=96 1x, /_next/image?url=…&w=256 2x">`. По запросу `/_next/image` сервер уменьшает картинку, конвертирует в WebP/AVIF и кэширует.

- Замер на нашем фото: исходник 640 px — 45 КБ, браузер получает **1,3 КБ** (обычный экран) или **4,5 КБ** (retina).
- `width`/`height` резервируют место — вёрстка не прыгает (CLS = 0).
- По умолчанию картинки грузятся лениво; для первого экрана — `preload` (в Next.js 16 заменил `priority`).
- `sizes` нужен только для резиновых картинок (ширина зависит от экрана). Для фиксированного аватара без `sizes` получаем ровно 1x и 2x; с `sizes` Next.js сгенерировал бы набор вплоть до 3840 px.

### `og:title`, `og:image`

Мета-теги протокола Open Graph в `<head>`: `<meta property="og:title" content="…">`, `<meta property="og:image" content="…/opengraph-image">`. Мессенджеры и соцсети (Telegram, Slack, LinkedIn, Upwork) читают их, когда в чат вставляют ссылку, и рисуют карточку-превью. Без них покажется голый URL или случайный кусок текста.

### Почему `/sitemap.xml` и `/robots.txt` открыты всем

Так и должно быть: их читают роботы, а робот — это анонимный посетитель без логина. В файлах только публичная информация.

- `robots.txt` — **просьба**, а не защита. Злоумышленник его просто проигнорирует. Защита `/admin` — авторизация и RLS (этап 2).
- Поэтому в `robots.txt` не перечисляют секретные адреса: это подсказка для атакующего.

### JSON-LD: где, кто создаёт, почему повторяется

- **Где:** корневой `layout.tsx` (Organization, WebSite) — на всех страницах; лендинг — FAQPage; профиль — Person с Offer и Service.
- **Кто создаёт:** разработчик. Next.js ничего не генерирует сам. Функции в `lib/seo/json-ld.ts` собирают объект из тех же данных, что и страница; компонент `JsonLd` выводит его в `<script type="application/ld+json">`.
- **Почему одинаковые на разных страницах:** Organization и WebSite описывают сайт целиком и стоят в общем layout. Это допустимо, но Google рекомендует держать их на главной; при желании можно перенести только туда.
- **Почему несколько на странице:** у каждой сущности свой блок — «сайт», «организация», «этот человек и его услуги».

### Зачем скрытый блок при стриминге, если данные приходят за миллисекунды

1. **Оболочка готова заранее.** Она отрендерена при сборке и отдаётся сразу, без работы сервера.
2. **Результаты считаются на каждый запрос** — они зависят от фильтров в URL. С Supabase это реальная задержка (десятки и сотни миллисекунд).
3. **HTML читается сверху вниз.** Начало документа уже отправлено, и дописать кусок в середину через HTML нельзя. Поэтому React отправляет результаты в конец ответа скрытым блоком и маленьким скриптом ставит их на место заглушки.
4. **Альтернатива — ждать данных и отправить всё разом.** Тогда пользователь смотрит на белый экран всё время, пока идёт запрос к базе. Стриминг даёт мгновенный первый экран.

**Робот не читает «мгновенно».** Он скачивает HTTP-ответ целиком, до закрытия соединения, и только потом разбирает. Стриминг — это один ответ, который приходит частями; робот ждёт его конца, как ждал бы медленный сервер, и получает и оболочку, и скрытый блок.

### Ловушка миграций: `create or replace view`

`create or replace view … as select …` **без** `with (security_invoker = true)` сбрасывает опцию (проверено в PGlite: `reloptions` становится `null`). Представление молча начинает обходить RLS. Поэтому опция повторена во второй миграции, а RLS-тест проверяет её на итоговом представлении.

## Сессия: cookies, proxy и `getClaims()`

- Сессия = access token (JWT, живёт час) + refresh token (одноразовый). `@supabase/ssr` хранит их в cookies,
  поэтому сервер видит пользователя при рендеринге.
- Истёкший токен обновляется refresh-токеном — и новые cookies надо отдать браузеру. Server Component
  записать cookies не может, поэтому это делает **`proxy.ts` до рендера**. Без этого — «пользователя
  выкидывает посреди действия» (скрининговый вопрос из плана).
- **`getClaims()`** проверяет подпись JWT. `getSession()` верит содержимому cookie — его можно подделать.
- Роль хранится в `profiles`, а не в JWT, и меняется только на сервере.

---

## Два слоя доступа: GRANT и RLS

- `GRANT` — к каким таблицам и **колонкам** роль имеет доступ: владелец может обновить `display_name`,
  но не `status`; пользователь — `full_name`, но не `role`.
- RLS — какие **строки**: клиент видит свои брони, специалист — брони с ним, админ — все.
- Проект создан без «Automatically expose new tables»: забыли `GRANT` — таблица закрыта, а не открыта всем.
- Одна политика на роль и действие (иначе Postgres проверяет каждую отдельно — замечание линтера).

---

## Функции базы: `SECURITY DEFINER` и `SECURITY INVOKER`

- **`SECURITY DEFINER`** — функция выполняется с правами владельца (обходит RLS). Так сделаны
  `book_slot()`, `cancel_booking()`, `apply_as_provider()`: клиент не может записать строку в `bookings`
  напрямую, но может попросить функцию, а функция сама проверяет `auth.uid()`, расписание, правило
  24 часов и берёт цену из базы.
- **`SECURITY INVOKER`** (по умолчанию) — права вызывающего, RLS действует внутри. Так сделана
  `replace_availability_rules()`: нужна только атомарность (вся неделя или ничего).
- У каждой функции `set search_path = ''`: имена не подменить объектами из другой схемы.
- Внутренние помощники для политик (`is_admin`, `owns_provider`) — в схеме `private`, которую Data API
  не публикует.

## Двойная бронь: почему ограничение, а не проверка

«Проверить, свободно ли, а потом вставить» — гонка: два запроса одновременно проходят проверку и оба
вставляют. Ограничение `EXCLUDE USING gist (provider_id with =, tstzrange(starts_at, ends_at) with &&)`
проверяет атомарно внутри базы: второй получает ошибку. `'[)'` — правая граница не включена, поэтому
бронь 10:00–11:00 и 11:00–12:00 не пересекаются. `where (status in (…))` — отменённые брони не мешают.

---

## Время: расписание локально, брони в UTC

- «Пн 9:00–13:00» хранится в поясе специалиста, бронь — `timestamptz` (точный момент).
- Весной 02:00–02:59 нет — такие слоты пропускаются; осенью этот час повторяется — один слот.
- Посетитель выбирает день в своём поясе; сервер узнаёт пояс из cookie `tz`, которую ставит браузер.
- Календарные даты — строки `"2026-11-03"`: арифметика дней без сюрпризов перехода времени.

## Формы: React Hook Form + Server Actions

- В браузере — мгновенные подсказки (RHF + та же Zod-схема), отправляется только валидная форма.
- `<form action={serverAction}>` работает и без JavaScript: тогда валидирует только сервер.
- **Сервер проверяет всегда** — браузерной проверке не доверяем.
- `autocomplete="current-password"` на входе, `"new-password"` при регистрации — менеджеры паролей
  понимают, что подставить и что предложить.
- Одинаковые сообщения для «нет такого email» и «неверный пароль» — не раскрываем, какие аккаунты есть.

## Безопасные редиректы после входа

`/login?next=…` — удобно, но опасно: `?next=https://evil.com` увёл бы пользователя на фишинговый сайт
сразу после входа (open redirect). `safeNext()` принимает только внутренний путь (`/account`), отклоняет
`//evil.com`, `/\evil.com` и всё, что после разбора URL указывает на другой домен.

## Ловушки, найденные тестами

- **`<fieldset>` не сжимается** уже содержимого (`min-width: min-content`) — горизонтальная лента дней
  растягивала страницу. Лечение: `min-w-0`.
- **`sr-only` внутри прокручиваемого блока** (`position: absolute`) вылезает за его пределы, если у
  родителя нет `position: relative`.
- **Next.js 16 хранит состояние недавно открытых страниц** при клиентской навигации — тест «вернулись
  к выбранному времени» проходил даже со сломанным восстановлением из URL. Перезагрузка в тесте.
- **`connection()`** — сказать Next.js «дальше только при реальном запросе»: проверка сессии использует
  текущее время, а оно запрещено при пререндере.
- **`create or replace view`** без `with (security_invoker = true)` сбрасывает опцию — представление молча
  обходит RLS.
- **Встроенная почта Supabase** отправляет письма только участникам проекта: для всех — свой SMTP.

### Идемпотентность простыми словами

Stripe гарантирует доставку «хотя бы один раз», а не «ровно один». Поэтому мы запоминаем id каждого
события (`stripe_events`, первичный ключ). Вторая доставка упирается в ключ — функция отвечает
`duplicate` и ничего не меняет. Запись id и изменение брони — в одной транзакции: не бывает
«событие записали, а бронь не подтвердили».

### Почему подписка перечитывается из Stripe

События могут прийти не по порядку: `updated` (active) раньше `created` (incomplete). Если
записывать то, что лежит в событии, последним окажется старое состояние. Мы берём из события
только id подписки и спрашиваем у Stripe текущее состояние — каким бы ни был порядок, итог верный.

### Почему не подтверждать бронь на странице успеха

Клиент мог закрыть вкладку (деньги списаны, брони нет) или открыть `/success` руками (бронь есть,
денег нет). Страница только показывает статус из базы и ждёт вебхук.

### Ловушки этапа

- **Минимальный срок Checkout — 30 минут.** Удержание 15 минут, поэтому задача раз в 5 минут
  закрывает Checkout просроченных броней, а поздняя оплата либо восстанавливает бронь, либо
  возвращается.
- **В тестовой базе у `service_role` не было `BYPASSRLS`**, как в настоящем Supabase: тест
  «повтор вебхука» падал не из-за кода, а из-за заглушки. Заглушка должна вести себя как оригинал.
- **Старая версия API аккаунта Stripe** (2019): события приходят без полей, которые читает код. Из
  события берём только id и перечитываем объект через SDK.
- **Adaptive Pricing** списал бы цену в евро — суммы и возвраты разошлись бы с ценой услуги.
  Выключено в Checkout брони.
- **`isVisible()` в Playwright не ждёт** — для «элемент может появиться» нужен `waitFor()`.
- **AFTER-триггер для лимита тарифа**: BEFORE-триггер срабатывает раньше RLS, и чужой пользователь
  получил бы ошибку о чужом тарифе вместо «нет доступа».
