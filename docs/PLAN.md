# Slotwise — план пет-проекта

Источник: «Slotwise — план пет-проекта» (Oct 13, 2026). Отметки `[x]` ставятся по мере выполнения.

## Цель и рамки

Slotwise — платформа бронирования для независимых специалистов: репетиторов, тренеров, коучей, массажистов. Цель — портфолио-кейс для Upwork, который закрывает самые частые требования фронтенд- и фулстек-вакансий и даёт реальный опыт бэкенда.

**Роли:**

- **Клиент** ищет специалиста, выбирает слот, платит, управляет записями.
- **Специалист** ведёт профиль, расписание и записи, платит подписку за платформу.
- **Админ** одобряет специалистов, модерирует, видит журнал действий.

**Принципы:**

1. Фронтенд — ядро, бэкенд — умеренный. Сложность бэкенда растёт от этапа к этапу.
2. Каждый этап задеплоен и показываем клиентам отдельно. Нельзя «копить» работу до конца.
3. Только бесплатные тарифы, кроме AI API (несколько долларов).
4. AI пишет код, но каждое решение ты можешь объяснить. Если не можешь — этап не закрыт.
5. Сначала работает, потом красиво, потом быстро. Но каждый этап заканчивается тестами.

## Архитектура

Один Next.js-проект: страницы, серверные действия и API-маршруты живут вместе, данные и авторизация — в Supabase. Внешние сервисы общаются с приложением через вебхуки.

- **Браузер** → страницы Next.js (Server Components для публичных страниц, Client Components для интерактива).
- **Мутации** (бронирование, профиль, отмена) → Server Actions → Supabase. Права проверяются на сервере и в RLS.
- **Оплата** → Stripe Checkout → вебхук на `/api/webhooks/stripe` → обработчик пишет в базу.
- **AI-чат** → `/api/chat` (стриминг) → модель вызывает инструменты → инструменты читают и пишут в Supabase с правами текущего пользователя.
- **Фон** → Inngest: напоминания, отмена неоплаченных броней, обработка документов для RAG.
- **Письма** → Resend, вызывается из фоновых задач и обработчиков.

```
slotwise/
├─ app/
│  ├─ (marketing)/          # лендинг, тарифы, каталог, профиль специалиста
│  ├─ (auth)/               # вход, регистрация, сброс пароля
│  ├─ (client)/account/     # кабинет клиента: мои записи
│  ├─ (provider)/dashboard/ # кабинет специалиста: расписание, записи, профиль, подписка
│  ├─ (admin)/admin/        # одобрение, модерация, журнал
│  └─ api/
│     ├─ webhooks/stripe/   # вебхуки Stripe
│     ├─ chat/              # AI-чат со стримингом
│     └─ inngest/           # точка входа фоновых задач
├─ components/
│  ├─ ui/                   # shadcn-компоненты, дизайн-система
│  └─ features/             # booking, chat, catalog и т.д.
├─ lib/
│  ├─ supabase/             # клиенты: browser, server, admin (service role — только сервер)
│  ├─ stripe/
│  ├─ ai/                   # промпты, инструменты, RAG
│  ├─ booking/              # расчёт слотов, правила отмены (чистые функции + тесты)
│  └─ validation/           # Zod-схемы
├─ inngest/                 # фоновые функции
```

## Модель данных и RLS

Схема создаётся только миграциями и растёт по этапам.

| Таблица                     | Ключевые поля                                                                                                                                                                                    | Этап          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------- |
| `profiles`                  | id (= auth.users.id), role: client / provider / admin, full_name                                                                                                                                 | 2             |
| `providers`                 | user_id, slug, display_name, headline, bio, city, timezone, status: pending / approved / rejected / suspended                                                                                    | 1 (чтение), 2 |
| `services`                  | provider_id, title, duration_min, price_cents, currency, active                                                                                                                                  | 1 (чтение), 2 |
| `availability_rules`        | provider_id, weekday, start_time, end_time (во времени специалиста)                                                                                                                              | 2             |
| `availability_exceptions`   | provider_id, date, start_time, end_time или весь день                                                                                                                                            | 2             |
| `bookings`                  | provider_id, client_id, service_id, starts_at, ends_at (timestamptz), status: pending_payment / confirmed / cancelled / completed / expired, price_cents, expires_at, stripe_checkout_session_id | 2             |
| `payments`                  | booking_id, stripe_payment_intent_id (unique), amount_cents, status, refunded_cents                                                                                                              | 3             |
| `provider_subscriptions`    | provider_id, stripe_customer_id, stripe_subscription_id, plan: free / pro, status, current_period_end                                                                                            | 3             |
| `stripe_events`             | id (= event.id, PK), type, received_at, processed_at                                                                                                                                             | 3             |
| `provider_documents`        | provider_id, title, storage_path, status: uploaded / processing / ready / failed                                                                                                                 | 4             |
| `document_chunks`           | document_id, provider_id, content, embedding vector, metadata                                                                                                                                    | 4             |
| `conversations`, `messages` | user_id, role, content, tool_calls                                                                                                                                                               | 4             |
| `ai_usage`                  | user_id, provider_id, tokens_in, tokens_out, cost_cents, created_at                                                                                                                              | 4             |
| `audit_log`                 | actor_id, action, entity, entity_id, data jsonb, created_at                                                                                                                                      | 5             |

**Защита от двойного бронирования — в самой базе.** Формат `[)` разрешает запись встык.

```sql
create extension if not exists btree_gist;

alter table bookings add constraint bookings_no_overlap
  exclude using gist (
    provider_id with =,
    tstzrange(starts_at, ends_at, '[)') with &&
  )
  where (status in ('pending_payment', 'confirmed'));
```

**RLS простыми словами:**

| Таблица                                   | Кто читает                                              | Кто пишет                                                                     |
| ----------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `profiles`                                | Владелец; админ — все                                   | Владелец свои поля, роль — только сервер                                      |
| `providers`, `services`, `availability_*` | Все — только одобренных; владелец — свои                | Владелец свои; статус — только админ                                          |
| `bookings`                                | Клиент — свои; специалист — свои записи; админ — все    | Создание — серверное действие от имени клиента; статус оплаты — только сервер |
| `payments`, `stripe_events`               | Никто из клиентов                                       | Только сервер (вебхук)                                                        |
| `provider_subscriptions`                  | Специалист — свою                                       | Только сервер (вебхук)                                                        |
| `provider_documents`, `document_chunks`   | Специалист — свои; поиск для AI — на сервере с фильтром | Специалист — свои документы; чанки — фоновая задача                           |
| `ai_usage`                                | Пользователь — свою; админ — все                        | Только сервер                                                                 |
| `audit_log`                               | Админ                                                   | Только сервер                                                                 |

Ключ `service_role` обходит RLS. Только в вебхуках и фоновых задачах, никогда в браузере.

## Рабочий цикл на каждую задачу

1. Пишешь задачу из плана в чат и просишь сначала план изменений.
2. Читаешь план, правишь, только потом разрешаешь писать код.
3. Читаешь диф. Всё про права, платежи, миграции и ключи — построчно.
4. Запускаешь и проходишь сценарий руками, включая плохие случаи.
5. Тесты зелёные, и ты проверил, что тест падает при поломке кода.
6. Коммит маленьким PR: что, зачем, как проверил, что не проверено.
7. Если AI ошибся и ты это поймал — одна строка в `docs/ai-catches.md`.
